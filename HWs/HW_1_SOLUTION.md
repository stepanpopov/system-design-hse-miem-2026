# HW1 — Нагрузочное тестирование demo-app-1

## 0. Окружение запуска

Стек поднимается одной командой `podman-compose up -d`. Каждый сценарий k6
запускается отдельным контейнером в host-network и пишет метрики в
Prometheus.

---

## Этап №1. Проектирование метрик

### 1.1 Логика приложения и потенциальные узкие места

Путь обработки запроса:

```
Browser
Nginx :8080
Backend :8081 
database/sql pool
PostgreSQL :5432
  (POST /api/orders идёт напрямую на :8081,
   GET /api/orders — через Nginx :8080)
```

Backend представляет собой тонкий слой: декодирование JSON, один SQL-запрос,
кодирование JSON. Кэш и тяжёлая бизнес-логика отсутствуют, поэтому узкое место
ожидается на I/O к базе данных либо на сетевом слое между Nginx и backend.

- `GET /api/orders` возвращает до 100 строк, сериализует их и проходит через
  reverse proxy, поэтому путь чтения длиннее и тяжелее пути записи.
- Пул соединений `database/sql` в исходном коде не ограничен: `SetMaxOpenConns`
  не вызывается, то есть `MaxOpenConns = 0` («открывать без ограничений»). При
  этом жёсткой лимит Postgres - `max_connections = 200`.

### 1.2 Отслеживаемые метрики (RED + USE)

Применяются две модели. RED описывает то, что наблюдает пользователь:

- Rate — RPS (`rate(http_requests_total[..])`, в k6 — `http_reqs`).
- Errors — доля 5xx (`http_req_failed`, `http_requests_total{status=~"5.."}`).
- Duration — латентность p95/p99 (гистограмма `http_request_duration_seconds`).

USE описывает состояние ресурсов и локализует затор:

- Utilization — CPU/RAM хоста (node_exporter), CPU контейнеров.
- Saturation — глубина очередей: число запросов «в полёте», число занятых
  соединений к БД, `WaitCount` пула, `node_load1`.
- Errors — ошибки базы данных и ошибки соединений.

RED отвечает на вопрос о деградации со стороны пользователя, USE — о её причине.

### 1.3 Недостающие метрики

Исходно backend экспортировал только `http_requests_total`,
`http_request_duration_seconds` и единственный `db_query_duration_seconds` без
меток. 
В `backend/main.go` добавлены следующие метрики:

| Метрика | Тип | Назначение |
|---|---|---|
| `http_requests_in_flight` | gauge | насыщение бэкенда — число запросов в обработке в текущий момент |
| `db_pool_open_connections` | gauge | число открытых соединений к БД (из `db.Stats()`) |
| `db_pool_in_use_connections` | gauge | число занятых соединений — прямой индикатор упора в БД |
| `db_pool_idle_connections` | gauge | простаивающие соединения (эффективность переиспользования пула) |
| `db_pool_wait_count` | gauge | число ожиданий свободного соединения |
| `db_pool_wait_seconds_total` | gauge | суммарное время ожидания соединения |
| `db_pool_max_open_connections` | gauge | текущий лимит пула (отражение конфигурации в метриках) |
| `db_errors_total{operation}` | counter | ошибки БД с разбивкой по операции (create_order, list_orders) |
| `db_query_duration_seconds{operation}` | histogram | длительность SQL с меткой операции |

Дополнительно лимиты пула вынесены в переменные окружения `DB_MAX_OPEN_CONNS` и
`DB_MAX_IDLE_CONNS` (поведение по умолчанию не изменяется). Это позволяет
переключать конфигурацию одной правкой в compose и воспроизводимо сравнивать
результаты «до» и «после», что использовано на Этапе №4.

## Этап №2. Сценарии обстрела

Скрипты расположены в `code/demo-app-1/k6/scripts/`. Распределение запросов
сохранено как в оригинале (80% POST `/api/orders`, 20% GET), за исключением
кастомного сценария, где оно изменено осознанно.

**«Шторм» (`storm.js`) — резкий пик.** `ramping-vus`: 0 → 1000 VU за 10 секунд,
удержание 1000 VU 30 секунд, спад до 0 за 20 секунд. Цель — проверить поведение
при резком броске нагрузки и восстановление после него.

**«Волна» (`wave.js`) — плавное нарастание.** `ramping-vus`: 0 → 500 VU за
2 минуты, спад до 0 за 30 секунд. Цель — поведение при медленном нарастании
нагрузки и поиск точки деградации.

**«Моя модификация» (`breakpoint.js`) — поиск потолка.** Вместо `ramping-vus`
(где число VU не равно числу запросов в секунду) используется
`ramping-arrival-rate`: executor задаёт целевой RPS, а не число пользователей, и
сам подбирает количество VU. Это позволяет правильно
определить потолок пропускной способности. Целевая нагрузка рампится
ступенями 50 → 2000 req/s. Соотношение смещено в сторону чтения (50% GET /
50% POST) для нагрузки на более тяжёлый путь (GET → Nginx → сериализация до
100 строк). При невозможности выдать заданный RPS k6 накапливает
`dropped_iterations` — прямой признак достижения предела системы.

Пример запуска:

```bash
podman run --rm --network host -v ./k6/scripts:/scripts:Z \
  -e K6_PROMETHEUS_RW_SERVER_URL=http://localhost:9090/api/v1/write \
  grafana/k6 run --out experimental-prometheus-rw /scripts/storm.js
```

## Этап №3. Анализ результатов

### Сводная таблица (исходная конфигурация, пул БД не ограничен)

| Метрика | Шторм | Волна | Breakpoint |
|---|---|---|---|
| Достигнутый RPS | ~977 | ~949 | ~627 (при запросе до 2000) |
| p95 латентности | 2.56 s | 757 ms | 2.94 s |
| p99 латентности | 5.19 s | 967 ms | ~10 s |
| max латентности | 37.2 s | 3.29 s | 39.2 s |
| Доля ошибок | 8.0% | 10.6% | 7.2% |
| Пик in-flight | 961 | 447 | 1995 |
| Пик занятых соединений к БД | 968 | 434 | 1996 |
| `pg numbackends` | до 55 | до 87 | до 28 |
| CPU хоста | ~59% | ~81% | ~50% |
| `node_load1` | ~20 | ~49 | ~33 |
| dropped_iterations | — | — | 22 585 |

### Инсайт 1. Главный ботлнек — слой соединений с БД

Под штормом метрика `db_pool_in_use_connections` достигла ~968: безлимитный пул
попытался открыть около тысячи соединений к Postgres при лимите 200. Логи базы
подтверждают это напрямую: `FATAL: sorry, too many clients already` — 159 записей
за первый же бросок. Эти отказы транслировались в ответы 500: число
`db_errors_total` совпало с числом 5xx один-в-один (4799 = 4799). Таким образом,
каждая ошибка приложения является отказом базы данных, а не дефектом логики.

Оставшиеся ошибки относятся к другому типу —
`read: connection reset by peer`. 
Причина —`MaxIdleConns` со значением по умолчанию 2: пул постоянно открывает и закрывает
сотни соединений, и под нагрузкой эти соединения разрываются. Накладные
расходы на TCP-handshake дополнительно увеличивают латентность.

Вывод: узкое место находится не в железе (CPU около 60%), а в нерегулируемом пуле
соединений. Система деградирует не плавно, а резко переходит в режим отказов,
когда конкурентность превышает лимит Postgres.

### Инсайт 2. «Волна» упирается в тот же потолок

Плавное нарастание до 500 VU не устранило проблему. Латентность остаётся
приемлемой (p95 = 757 ms, поскольку успешные запросы быстрые), однако доля ошибок
составляет 10.6%: при превышении ~200 одновременных запросов лишние получают
отказ. Практический вывод: ведущим индикатором здесь является не латентность, а
error rate. Ошибки «быстрые», они почти не растягивают перцентили, поэтому по
графику латентности проблему легко пропустить.

### Инсайт 3. Потолок пропускной способности — около 600–650 RPS

Breakpoint-тест запрашивал до 2000 req/s, но система отдала лишь ~627 RPS при
22 585 `dropped_iterations` — k6 физически не смог разместить нагрузку. Это и есть
фактический потолок текущей конфигурации (один инстанс backend, один Postgres,
безлимитный пул): до ~600 RPS.

### Инсайт 4. Путь чтения слабее пути записи

В breakpoint-тесте GET `/api/orders` отказывал на ~14%, POST — на ~0.5%. Чтение
тяжелее: проходит через Nginx и сериализует до 100 строк. При этом число ошибок
GET существенно превышало число ошибок БД для `list_orders`, то есть часть
отказов чтения возникает до базы — на слое reverse proxy и соединений. Это
указывает на второй ботлнек — Nginx.

## Этап №4. Решения и их проверка

### Решение 1 (основное): ограничить и переиспользовать пул соединений

В `backend/main.go` добавлена конфигурация пула через окружение, значения заданы в
`docker-compose.yaml`:

```yaml
backend:
  environment:
    DB_MAX_OPEN_CONNS: "80"   # db.SetMaxOpenConns(80) — меньше, чем обслуживает Postgres
    DB_MAX_IDLE_CONNS: "40"   # db.SetMaxIdleConns(40) — переиспользование
```

Принцип: ограничить конкурентность к БД числом, которое Postgres гарантированно
обслуживает (80 < 200), а избыток запросов ставить в очередь внутри
приложения (быстрое in-memory ожидание свободного соединения) вместо отказов на
стороне базы.

Для проверки выполнен повторный «Шторм» с тем же профилем (0 → 1000 VU) на той же
базе с теми же данными (~255k строк в `orders`):

| Метрика | Шторм ДО (пул ∞) | Шторм ПОСЛЕ (пул 80) |
|---|---|---|---|
| RPS | 977 | 4226 | ×4.3 |
| p95 | 2.56 s | 455 ms | в 5.6 раза быстрее |
| max | 37.2 s | 8.1 s | в 4.6 раза быстрее |
| Ошибки POST (`create_order`) | ~8% | 0% | ошибки пропали |
| Прирост `db_errors_total` | +4799 | +0 | ошибки пропали |
| Пик соединений к БД | 968 | 80 | ровно лимит |

`db_errors_total` перестал расти, `too many clients` в логах исчез, пропускная
способность выросла в четыре раза.

### Решение 2: после фикса БД ботлнек смещается на Nginx

Тот же обстрел «после фикса»: POST - 0 ошибок,
GET начал отдавать `HTTP 502 Bad Gateway` (в отдельном GET-обстреле на 1000 VU —
около 21% таких ответов). При этом `db_errors_total` для `list_orders` не рос,
следовательно 502 генерирует сам Nginx, не доходя до backend. Причина —
стандартный `proxy_pass` без upstream keepalive: на каждый запрос открывается
новое соединение к backend.

Решение (следующий шаг):

```nginx
upstream backend_up {
    server backend:8081;
    keepalive 64;                 # пул постоянных соединений к backend
}
server {
    location /api/ {
        proxy_pass http://backend_up/api/;
        proxy_http_version 1.1;
        proxy_set_header Connection "";   # включение keepalive к upstream
    }
}
```

При необходимости дополнительно повышаются `worker_connections` и
`keepalive_requests`.

### Решение 3: горизонтальное масштабирование

- Использовать `docker-compose-lb.yaml` (HAProxy + 3 инстанса backend,
  round-robin), что снимает потолок одного инстанса.
- Для тяжёлого чтения (`GET /api/orders`) применить кэш (Redis) или read-реплики
  Postgres, поскольку список заказов изменяется не на каждый запрос.
- Добавить пагинацию вместо `LIMIT 100` и сортировку по индексу.

### Решение 4: устойчивость к перегрузке

- Таймауты на SQL-запрос (`context.WithTimeout`) и на HTTP-сервер
  (`ReadTimeout` / `WriteTimeout`), чтобы зависшие запросы не
  накапливались.
- Rate limiting: при перегрузе предпочтительнее быстрый
  ответ 503, чем накопление длинных хвостов.
- Подбор `DB_MAX_OPEN_CONNS` с учётом кластера: `N_инстансов × MaxOpenConns`
  должно быть меньше `max_connections` Postgres.

## Итоги

1. Главный ботлнек — безлимитный пул `database/sql` при `max_connections=200` у
   Postgres. Под пиком возникают `too many clients` и `connection reset`, 8–11%
   ошибок во всех сценариях. CPU узким местом не является (~60%).
2. Потолок исходной конфигурации — около 600–650 RPS (breakpoint, 22 585 dropped
   iterations при запросе 2000 RPS).
3. Чтения (GET через Nginx) тяжелее записи: 14% против 0.5% ошибок.
4. Фикс пула (80/40) дал ×4.3 по RPS, p95 в 5.6 раза быстрее и обнулил ошибки
   записи — диагноз подтверждён экспериментально.
5. После фикса ботлнек смещается на Nginx (502 из-за отсутствия upstream
   keepalive) — обозначен следующий шаг оптимизации.
