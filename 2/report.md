## Исходное задание
Your Architectural Kata is...  
Check Your Work
A university has greatly expanded its CS course and wants to be able to automate the grading of simple programming assignments.

Users: 300+ students per year, plus staff and admin.

Requirements: Students must be able to upload their source code, which will be run and graded. Grades and runs must be persistent and auditable. There must be a plagiarism detection system involving comparing with other submissions and also submitting to a web-based service (TurnItIn). There must be some level of integration with the University's learning management system (LMS)

## Описание кейса
**Check Your Work** — университетская система автоматической проверки простых программных заданий. Студенты загружают исходный код, он запускается и оценивается. Результаты и прогоны должны храниться и быть проверяемыми (аудируемыми). Встроена проверка на плагиат (сравнение с другими работами и отправка в веб-сервис TurnItIn). Требуется интеграция с LMS вуза.

**Пользователи:** 300+ студентов в год, преподаватели (staff) и администраторы.

## 1. Отсев

На старте имеем ряд «сырых» пожеланий заказчика. Не все из них одинаково проработаны или реализуемы в первой версии.

| Исходная идея / требование | Решение | Обоснование |
|---|---|---|
| Автоматическая проверка любых языков программирования | Начинаем с Python и Rust | Каждый новый язык требует отдельный сэндбокс и набор тестов; расширять будем постепенно |
| Полноценный AI-ассистент, дающий студенту развёрнутый фидбек по коду | Исключён из MVP | Значительно увеличивает стоимость и сложность; в первой версии — вывод результатов тестов и сообщений компилятора |
| Интеграция с произвольными внешними сервисами проверки на плагиат | Только TurnItIn | Прямо указано в требованиях; дополнительные сервисы — позже |
| Поддержка мобильных устройств как полноценного клиента | Веб-интерфейс, адаптированный для мобильных браузеров (PWA) | Нативное мобильное приложение избыточно для MVP |
| Real-time панель мониторинга для деканата | Отложена | Сначала — отчёты по запросу; дашборды войдут во вторую очередь |
| Поддержка SaaS-модели для других вузов | Архитектура закладывается мультиарендной, но первый релиз — один вуз | Требование не заявлено явно; изоляция данных — на уровне схем БД |

**Принятые в MVP блоки:**
- загрузка исходного кода студентом;
- автоматический прогон в изолированном окружении (сэндбоксе);
- автоматическое выставление оценки по заранее заданным критериям;
- сохранение всех результатов и истории запусков;
- проверка на плагиат (внутреннее сравнение + TurnItIn);
- интеграция с LMS вуза (REST API);
- роли: студент, преподаватель, администратор.

## 2. Scope Refinement (уточнение границ)

### Типы пользователей
- **Студент:** загружает решения, видит свои оценки и результаты прогонов, получает фидбек.
- **Преподаватель:** создаёт/редактирует задания, настраивает тест-кейсы и критерии оценки, просматривает результаты студентов, запускает проверку на плагиат, выставляет финальную оценку (при необходимости корректирует автоматическую).
- **Администратор системы:** управляет учётными записями, курсами, связью с LMS, конфигурацией сэндбоксов.
- **Интеграционная учётная запись LMS:** сервисный аккаунт для обмена данными (передача оценок, получение списка студентов).

### Ключевые объекты предметной области
- **Assignment (задание):** описание, дедлайн, набор тест-кейсов, критерии оценки.
- **Submission (попытка):** загруженный исходный код, временная метка, статус проверки.
- **Test Run (прогон):** результат компиляции, вывод тестов, ошибки, время выполнения.
- **Grade (оценка):** computed (автоматическая) и final (скорректированная преподавателем).
- **Plagiarism Report:** результат сравнения, процент схожести, ссылки на похожие работы.

### Границы первой версии
**Включено:**
- Поддержка языков Python 3.12+ и Rust 1.95+.
- Загрузка одного файла или zip-архива с исходным кодом.
- Автоматический прогон на заранее определённом наборе тестов.
- Оценка «зачёт/незачёт» (pass/fail) с возможностью перевода в баллы.
- История всех попыток студента с таймстемпами.
- Запуск проверки на плагиат по требованию преподавателя.

**Не включено в MVP:**
- Проверка стиля кода (linting) и дополнительных code quality метрик.
- Peer-review (проверка студентами решений других студентов).
- Интерактивная отладка в браузере.
- Поддержка GUI-приложений и фреймворков.

## 3. Функциональные требования

#### Управление заданиями
- FR-01: Преподаватель может создать задание с указанием названия, описания, языка программирования, дедлайна, набора тест-кейсов и критериев прохождения.
- FR-02: Преподаватель может редактировать параметры задания, включая тест-кейсы, до первой попытки студента (после — только с флагом «пересчитать оценки»).
- FR-03: Преподаватель может архивировать задание (скрыть от студентов) и удалять.

#### Загрузка и проверка решений
- FR-04: Студент может загрузить исходный код (один файл или zip-архив) через веб-интерфейс.
- FR-05: Система автоматически компилирует (если требуется) и запускает код в изолированном Docker-контейнере с ограничением по CPU, памяти и времени (настраивается на задание).
- FR-06: Система прогоняет код на всех тест-кейсах и фиксирует результат каждого: passed / failed / error.
- FR-07: Студент получает отчёт: общий вердикт (pass/fail), пройденные и упавшие тесты, вывод компилятора, stdout/stderr (без раскрытия содержимого скрытых тестов).

#### Оценивание
- FR-08: Система автоматически вычисляет оценку согласно критериям задания (например, pass = 100% тестов пройдено).
- FR-09: Преподаватель может скорректировать автоматическую оценку вручную с обязательным комментарием.
- FR-10: Преподаватель может выгрузить ведомость оценок в формате CSV/Excel.

#### Проверка на плагиат
- FR-11: Преподаватель может инициировать проверку на плагиат: сравнение выбранной работы со всеми остальными работами в системе.
- FR-12: Преподаватель может отправить работу в TurnItIn через API; результат сохраняется в системе как Plagiarism Report.
- FR-13: Система отображает процент схожести и список похожих работ с возможностью просмотра diff-а.

#### Интеграция с LMS
- FR-14: Система получает из LMS список курсов, студентов и преподавателей (через REST API).
- FR-15: Система передаёт в LMS итоговые оценки студентов.

#### Аудит
- FR-16: Все изменения оценок, параметров заданий и запуски проверок логируются с указанием пользователя и временной метки.

## 4. Нефункциональные требования

#### Производительность и масштабируемость
- NFR-01: Время ответа веб-интерфейса (загрузка страницы, отправка формы) не превышает 2 секунды для 95-го перцентиля.
- NFR-02: Время от загрузки решения до получения результата проверки — не более 30 секунд для 95% попыток при условии очереди не более 50 заданий.
- NFR-03: Система должна поддерживать горизонтальное масштабирование: добавление новых worker-узлов для запуска кода без остановки сервиса.
- NFR-04: Пропускная способность — не менее 10 одновременных прогонов кода на одном worker-узле.

#### Доступность и надёжность
- NFR-05: Доступность системы — 99.5% в месяц (~3.6 часов простоя), исключая плановые окна.
- NFR-06: RTO (целевое время восстановления) — 1 час, RPO (точка восстановления данных) — не более 1 минуты.
- NFR-07: Все результаты прогонов и оценки должны быть персистентными (запись в БД до отправки ответа студенту).

#### Безопасность
- NFR-08: Весь внешний трафик — HTTPS (TLS 1.3).
- NFR-09: Аутентификация — через единую учётную запись вуза (SSO) либо логин/пароль с обязательным 2FA для преподавателей и администраторов.
- NFR-10: Пароли хранятся в виде bcrypt/scrypt хешей. Персональные данные — в зашифрованном виде (AES-256).
- NFR-11: Запуск кода студентов — в строго изолированных контейнерах, без доступа к сети, с лимитами ресурсов. Защита от fork-bomb, инъекций и утечек.
- NFR-12: Защита от OWASP Top-10 на уровне кода и WAF.

#### Наблюдаемость
- NFR-13: Централизованный сбор логов, метрик (Prometheus).
- NFR-14: Алертинг на критические события: падение worker-а, рост очереди > 100, ошибки 5xx > 1%.

#### Совместимость и развёртывание
- NFR-15: Серверная часть — контейнеризованная (Docker), оркестрация — Kubernetes или Docker Compose (для малых инсталляций).
- NFR-16: Поддержка браузеров: Chrome 100+, Firefox 100+, Safari 15+, Яндекс.Браузер последней версии.

## 5. Ограничения

#### Законодательство и регуляторика (РФ, 2026)
- **152-ФЗ «О персональных данных»:** персональные данные студентов и преподавателей (ФИО, email, идентификаторы) должны храниться и обрабатываться на серверах, физически расположенных на территории РФ. Использование зарубежных облачных провайдеров (AWS, Azure, GCP) в качестве первичного хранилища недопустимо. 
- **Импортозамещение:** приоритет на использование российского ПО.
- **TurnItIn:** внешний сервис, работающий через API. Поскольку данные отправляются на зарубежный сервис, необходимо получить согласие субъектов ПДн и зафиксировать это в политике обработки данных.

#### Инфраструктурные
- SaaS не предполагается — система разворачивается в контуре одного университета (on-premise или в частном облаке вуза).
- Бюджет ограничен: стартовая инфраструктура — 2-3 физических сервера или эквивалентные виртуальные машины.

#### Технологические
- Сэндбоксинг: контейнеры Docker обязательны для безопасного исполнения студенческого кода.
- Интеграция с LMS: REST API конкретной LMS вуза.

## 6. Расчёт нагрузки

### Пользовательская база
- Студентов в год: 350 (с запасом на рост набора).
- Преподавателей и администраторов: ~10 человек.
- Итого активных учётных записей: **360**.
- **MAU** = 360 (все активны ежемесячно в течение семестра).
- **DAU** (средний) = 50% от MAU = **180** (пик в дни дедлайнов; в такие дни DAU может достигать 300).

### Характер трафика и RPS

Для оценки пиковой нагрузки рассматриваем **неделю перед дедлайном**, когда активность максимальна.  
WAU в эту неделю принимается равным 360 (все пользователи).

Операции пользователей за пиковую неделю:

| Роль | Действие | Среднее количество в неделю на пользователя |
|---|---|---|
| Студент | Загрузка решения (POST с файлом) | 15 |
| Студент | Просмотр результата (GET) | 30 |
| Преподаватель | Создание / редактирование задания (CRUD) | 2 |
| Преподаватель | Просмотр ведомости (GET) | 4 |
| Преподаватель | Запуск проверки на плагиат (POST) | 2 |

**Суммарное количество запросов за пиковую неделю:**
- Студенты: 350 × (15 + 30) = 15 750 запросов.
- Преподаватели: 10 × (2 + 4 + 2) = 80 запросов.
- **Итого:** 15 830 запросов / неделя.

**Среднее количество запросов в день в пиковую неделю:**  
15 830 / 7 ≈ **2 261 запрос / день**.

**Базовый средний RPS в пиковую неделю:**  
2 261 / 86 400 ≈ **0.026 req/s**.

**Пиковый час (день дедлайна):**
- В час дедлайна может концентрироваться до **50% суточной нагрузки**.
- Количество запросов в пиковый час: 2 261 × 0,5 ≈ **1 131 запрос**.
- Значительная часть из них — загрузки решений (пиковая частота загрузок ≈ 375 операций в час).
- Пиковый RPS по API: 1 131 / 3 600 ≈ **0,31 req/s**.

Основная нагрузка в пике определяется не столько HTTP-запросами, сколько **очередью прогонов** кода. При 375 загрузках в час и среднем времени запуска до 30 секунд на одно решение, в очереди может одновременно находиться до **60 заданий**. Два worker-узла, способных выполнять до 20 прогонов каждый, справляются с такой нагрузкой.

**Проектный пиковый RPS с запасом (×5 для API и статики):** ~ **3 req/s**.

### Сетевой трафик
- Средний размер загружаемого решения (один файл .py / .rs): 2–10 КБ.
- Средний размер JSON-ответа (результаты тестов): 1–3 КБ.
- Статика (PWA): отдаётся тем же веб-сервером (Nginx) с долгосрочным кешированием на клиенте; отдельный внешний CDN не используется.
- **Исходящий трафик в пике:** 3 req/s × 3 КБ ≈ 9 КБ/с. Достаточно канала 100 Мбит/с.

### Дисковое пространство (прогноз на 5 лет)

#### Полезные данные

| Объект хранения | Размер единицы | Количество | Итого |
|---|---|---|---|
| Учётные записи пользователей | 1 КБ | 2 000 (рост за 5 лет) | 2 МБ |
| Задания (описание, тесты) | 50 КБ | 100 | 5 МБ |
| Попытки (исходный код) | 5 КБ | 350 студ. × 10 попыток × 5 заданий × 5 лет = 87 500 | 440 МБ |
| Результаты прогонов (JSON) | 2 КБ | 87 500 | 175 МБ |
| Отчёты о плагиате | 10 КБ | 5 000 | 50 МБ |
| Логи аудита | 100 байт на запись | ~500 000 | 50 МБ |

Полезные данные: ~0,7 ГБ за 5 лет. С учётом репликации (×2) и бэкапов (×3) — **~5 ГБ** дискового пространства.

#### Логи контейнеров и хранение образов.

Отдельно выделим каждому инстансу по 10GB на логи, и хранение docker образов.  
Этого точно хватит, чтобы увидеть историю за несколько последних дней.  
Для логов настроим политику ротации, чтобы диск не переполнялнялся.

### Нагрузка на базу данных
- QPS: проектные 3 req/s пиковых, из них запись — 40% (1,2 req/s), чтение — 60% (1,8 req/s).
- Одна инстанция PostgreSQL (даже минимальной конфигурации) держит 500–1000 QPS — более чем достаточно.
- Для отказоустойчивости: primary + standby (асинхронная репликация), RPO ~ 1 минута.

### Оценка вычислительных ресурсов

| Компонент | Конфигурация | Количество | Назначение |
|---|---|---|---|
| Сервер приложений | 2 vCPU, 4 ГБ RAM | 2 реплики | Веб-интерфейс + API |
| Worker для прогонов | 4 vCPU, 8 ГБ RAM | 2 реплики (до 20 одновременных контейнеров) | Запуск кода в Docker-сэндбоксах |
| База данных | 2 vCPU, 4 ГБ RAM, 50 ГБ SSD | 1 primary + 1 standby | PostgreSQL 16 |
| Файловое хранилище | S3-совместимое (MinIO) | 100 ГБ | Хранение исходного кода попыток |

**Итого:** 6 виртуальных машин (суммарно ~16 vCPU, 32 ГБ RAM), что укладывается в 2-3 физических сервера среднего класса.

### Ограничения на рост
При увеличении потока студентов система масштабируется добавлением worker-узлов (горизонтальное масштабирование очереди прогонов).
